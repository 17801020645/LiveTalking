# 目标

管理员在管理后台可以对普通用户点「禁用」。禁用后该用户不能登录，已有会话失效。复用已有 `POST /api/v1/admin/users/{id}/disable`，本轮补页面与验收，不做启用或删除。

# 范围

- `/app/admin/ops` 用户表：对 `role=user` 且 `status=active` 的行提供禁用按钮；点按先确认再调用现有禁用接口
- 不能禁用当前登录账号；管理员行不出现禁用按钮
- 禁用后列表状态变为 `disabled`；该用户再用原密码登录失败（统一「用户名或密码错误」）
- 补单测覆盖禁用权限、禁自己、禁后不能登录
- 更新 `auth-rbac` 与 `web-app-shell` 中管理后台用户管理描述

# 非目标

- 不做启用/恢复、删除用户、代人改密、自助注册、邮箱验证码
- 不改默认入口、ASR、`web/`、Gallery 视觉
- 不强制结束 WebRTC 连麦会话（只清平台登录 Cookie 会话）

# 验收示例

- A1：管理员在管理后台对普通活跃用户点禁用（经确认）后，该行状态为 `disabled`
- A2：被禁用用户登录返回与错误密码相同的失败文案，进不了 `/app`
- A3：管理员不能禁用当前登录账号；对管理员行没有禁用按钮；未登录 401，普通用户调禁用接口 403
- A4：`web/` 无改动；开户、绑定、订单、Gallery 行为不因本 change 改变

# 约束与不变量

- 工作区：main 当前目录（`isolation: current`）
- 沿用现有禁用 API 语义：只更新 `role=user`，并删除该用户平台会话
- 失败登录仍不泄露账号是否存在

# 决策

- 切片：只做禁用，页面接上已有 API
- 隔离：当前目录 main
- 不做启用；禁用后不能从后台撤销
- 点禁用先确认，避免误触
